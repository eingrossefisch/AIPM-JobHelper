## 3️⃣ 八股背诵

| :--- | :--- | :--- | :--- |
| **训练范式：预训练 vs 微调** | 预训练（Pre-training）和微调（Fine-tuning）有什么区别？在产品落地里你怎么选：直接用API、做RAG、还是做微调？ | **一句话解释**：预训练是“打通用底座能力”，微调是“把底座的输出风格/领域能力往目标任务上掰正”，而RAG是“让模型在推理时带着最新/私有资料开卷考试”。<br><br>**核心区别**：<br>1) **目标**：预训练学通用语言/世界知识；微调学特定任务分布（客服话术、字段抽取风格、工具调用格式等）。<br>2) **数据**：预训练海量通用数据；微调用高质量的任务数据（成对指令-答案/偏好数据）。<br>3) **成本与周期**：预训练成本最高（通常不是业务团队可选项）；微调成本中等（数据准备+训练+评测+部署）；API/RAG迭代最快。<br><br>**选型决策（面试建议按“先快后重”讲）**：<br>**① 先用 API + Prompt**：当问题主要是“表达方式/流程引导”而非知识缺失，例如：回复结构、口吻统一、输出JSON。优点是上线快、成本低；缺点是稳定性受提示词影响。<br>**② 用 RAG**：当痛点是**知识更新快、私有资料多、需要可追溯引用**（政策、产品手册、工单知识库）。优点是“内容可控、可更新”；代价是检索链路带来延迟与工程复杂度。<br>**③ 再考虑微调（含LoRA/PEFT）**：当你已经有稳定数据闭环且需求是**“持续稳定的格式/风格/领域判别能力”**，比如：意图识别、结构化抽取、固定话术合规、工具调用准确率。优点是更稳定、更省token；代价是数据与评测投入大、版本管理复杂。<br><br>**产品化落地提醒**：微调前先问三件事——是否有≥几千条高质量样本？是否有明确线上指标（准确率/通过率/节省时长）？是否能承担回归测试与灰度？否则容易“花钱变差”。 | 是否能把“技术能力”转成“产品选型与ROI”语言；是否理解 RAG/Prompt/微调的边界、成本与迭代节奏。 |
| **推理与Prompt：CoT / Reasoning** | 什么是 CoT（思维链）？它为什么能提升效果？在真实产品里你会怎么用、怎么控风险？ | **一句话解释**：CoT 是让模型“先写出中间推理步骤再给答案”，相当于把复杂题拆小步骤执行，从而提升复杂推理/多约束任务的成功率。<br><br>**优势（讲到“适用场景”就很面试加分）**：<br>1) **复杂任务更稳**：多步计算、对比权衡、规则检查、长文本归纳（如：合同要点+风险点+建议）。<br>2) **可调试**：中间步骤暴露后，PM更容易定位失败是“理解错、信息缺、还是步骤跳了”。<br>3) **适合Agent规划**：CoT/Plan 能帮助模型先做任务分解，再逐步调用工具。<br><br>**Trade-off（必须主动讲缺点）**：<br>1) **成本更高**：输出更长→token成本与延迟上升。<br>2) **泄露风险**：中间推理可能包含敏感信息或“越权推理”。<br>3) **不等于更真实**：推理写得像样也可能是“编出来的”。<br><br>**产品落地用法（推荐面试回答框架）**：<br>**① 内部CoT、外部短答**：让模型在“隐藏思考”完成推理，但对用户仅展示结论+依据要点，降低泄露与冗长。<br>**② 用“结构化步骤”替代自由发挥**：例如“先列约束→再列候选→打分→给最终方案”，减少胡乱展开。<br>**③ 与检索/工具校验结合**：CoT过程中强制引用RAG证据或调用计算器/规则引擎；无证据则降级为“无法确认”。<br>**④ 指标化评估**：不只看“回答像不像”，要看任务成功率（Task Success）、一致性（Consistency）、以及成本（avg tokens/latency）。 | 是否理解 CoT 的本质是“提示与过程控制”，并能说清成本/风险；是否具备把 CoT 融入 Agent/RAG/评测的产品化方法。 |
| **可靠性：幻觉治理（Hallucination）** | 大模型“幻觉”是什么？如果你的AI客服/知识助手频繁编造信息，你会怎么缓解与治理？ | **一句话解释**：幻觉是模型在缺少可靠依据时仍“自信生成”看似合理但不真实的内容，本质是生成式模型的概率补全机制与知识/上下文缺口共同导致。<br><br>**常见诱因（面试要能分类）**：<br>1) **知识缺口**：训练知识过期、企业私有知识不在模型里。<br>2) **上下文不足/检索失败**：没拿到相关文档，或召回不准、切片不合理。<br>3) **指令冲突**：既要“必须回答”又要“不能编”，模型倾向迎合。<br>4) **评测与反馈缺失**：上线后没有监控“高风险回答”。<br><br>**治理策略（按“预防-过程-兜底-复盘”讲，最像真实PM）**：<br>**① 预防：让模型有资料可依**：上RAG/知识库，建立内容更新机制；对高频问答做“权威答案库”。<br>**② 过程控制：强制可追溯**：要求回答必须给出**引用来源/链接/文档片段**；无引用则输出“我查不到”并引导转人工。<br>**③ 风险分级与场景收窄**：把问题分为低/中/高风险（如医疗、金融、法律为高风险），高风险场景默认“只总结引用内容，不给结论性建议”。<br>**④ 置信度与多模型校验**：用检索得分、规则校验、或第二模型做“事实一致性检查/自检”；低置信度触发降级。<br>**⑤ 人工兜底与可观测性**：高风险答复走人工审核；建立线上监控：幻觉投诉率、无引用回答占比、被纠错率、Top失败Query榜单。<br>**⑥ 闭环优化**：把真实对话中“用户纠错/人工修改/差评”沉淀为评测集与微调数据（或用于RAG文档补齐）。<br><br>**一句话总结给面试官**：幻觉不是靠一句prompt消失的，要用“数据供给（RAG/知识库）+过程约束（引用/校验）+风险兜底（人工/降级）+评测闭环”系统治理。 | 是否能从产品风险与工程链路角度系统治理幻觉；是否具备指标体系、分级策略与上线后的监控/闭环意识。 |
