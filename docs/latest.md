### **专家级面试真题深度解析 (QA)**

#### **1. 百度：如何构建模型选择的决策框架 (A: 大模型高质量慢速 vs B: 小模型中质量快速)？**
*   **面试考点：** 考查 PM 的 **ROI 意识** 与 **场景拆解能力**。
*   **参考答案：** 
    1.  **用户场景分类**：根据任务复杂度路由。简单问候、事实性查询（如天气）走 B 模型；逻辑推理、创意写作走 A 模型。
    2.  **容错度评估**：若为金融/医疗等严肃场景，20% 错误率不可接受，必须选 A 或辅以人工校验；若为闲聊/娱乐场景，优先选 B 保证响应速度。
    3.  **漏斗分流**：先由 B 模型生成初稿并由判断模型（Evaluator）打分，若低于阈值，再触发 A 模型重写，以此平衡成本与体验。

#### **2. 网易互娱：如何定义 AI 观点总结功能的“上线标准”？**
*   **面试考点：** 考查 **指标体系构建** 与 **工程落地经验**。
*   **参考答案：**
    1.  **准确性指标**：建立 Baseline 数据集，通过人工标注（Ground Truth）对比模型输出，核心观点召回率需 > 90%，事实错误率（幻觉率）需 < 5%。
    2.  **工程性能指标**：首字响应时间（FBFT）需控制在 1s 内，整体生成速度需适配阅读节奏。
    3.  **用户反馈循环**：上线前需经过 A/B Test，对比 AI 总结版与纯文本版的点击率（CTR）及用户满意度评分（CSI），只有在关键业务指标不下降且满意度显著提升时才准予发布。

| **Tool Calling** | 讓 LLM 進行 Tool Call（工具調用）與讓 LLM 寫 Python 代碼執行函數，兩者有什麼區別？PM 該如何選擇？ | **通俗解釋**：Tool Call 是給 AI 一套“標準說明書”，由系統去執行；寫代碼是讓 AI 自己“現編現造”並運行。<br>**1. 穩定性**：Tool Call 遵循 JSON Schema 格式，結構化強，適合與企業內部的數據庫、API 對接，出錯率低。<br>**2. 靈活性**：寫代碼（Code Interpreter）適合處理動態計算或數學問題，但有代碼注入的安全風險，且輸出不穩定。<br>**3. 決策建議**：業務邏輯固定（如查庫、訂票）選 Tool Call；探索性任務（如數據分析、畫圖）選寫代碼。 | 考察對 LLM 與外部系統交互邏輯的理解，以及對安全性和確定性的權衡。 |
| **成本與性能優化** | 在設計 AI Agent 或 RAG 系統時，有哪些具體的成本優化經驗？ | **通俗解釋**：通過“省著用、用便宜的、少重複用”三個原則來控制 Token 支出。<br>**1. 數據側**：在 RAG 檢索時優化 Chunk 顆粒度，過濾無效信息，減少輸入上下文的 Token 數量。<br>**2. 模型路由 (Router)**：簡單任務（如分類、總結）交給輕量級小模型（如 GPT-4o-mini）；複雜邏輯（如推理、規劃）再調用昂貴的大模型。<br>**3. 緩存策略**：使用 Prompt Cache 技術，對重複出現的系統提示詞或背景文檔進行緩存，降低高達 50% 以上的重複計算成本。 | 考察對 AI 產品商業化成本（ROI）的敏感度及工程落地方案的成熟度。 |
| **長文本生成** | 面對 2000 字以上的長文本生成需求，AI 常會“虎頭蛇尾”或邏輯崩潰，你如何解決這個問題？ | **通俗解釋**：不要讓 AI “一次成稿”，而是通過“分模塊工作流”來實現。<br>**1. 任務拆解**：設計多步驟 Agent，第一步生成詳細大綱，第二步分章節填充，第三步進行全文邏輯檢查。<br>**2. 結構化提示**：使用 CoT（思維鏈）引導 AI 先思考每一段的核心觀點，再展開寫作，避免上下文漂移。<br>**3. 緩解“復讀機”**：針對長文本易出現的重復問題，調整模型的 `frequency_penalty` 參數，並在 Prompt 中明確禁止特定的口水話。 | 考察對模型注意力限制（Context Window）的理解，以及對複雜任務流（Workflow）的設計能力。 |
