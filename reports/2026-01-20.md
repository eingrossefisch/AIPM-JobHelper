## 3️⃣ 八股背诵
| 领域 | 问题 (Q) | PM解答 (A) | 考察点 |
| :--- | :--- | :--- | :--- |
| **训练范式（Pretrain vs Fine-tune）** | 预训练（Pre-training）和微调（Fine-tuning）有什么区别？在产品里你会如何选择“用 API + Prompt / RAG”还是“做微调”？ | **通俗解释**：预训练是在“通识教育”，微调是在“岗位培训”；但很多产品问题其实靠“提示词+外部知识/工具”就能解决，不一定要改模型。<br><br>**1）核心区别**<br>• **预训练**：用海量通用数据学习语言与世界知识，得到“通用能力底座”。成本极高（算力/数据/周期），通常只有大厂或模型厂做。<br>• **微调**：在特定任务/领域数据上继续训练，让模型更贴合特定风格、格式、流程或特定领域分布。成本相对低，但仍有数据工程、训练与回归评测成本。<br><br>**2）产品侧怎么选（决策框架）**<br>• **优先用 Prompt/工作流**：需求是“回答方式/结构化输出/角色语气/流程遵循” → 先用系统提示词、few-shot、模板化输出、函数调用（tool calling）就能明显提升，成本最低、迭代最快。<br>• **用 RAG**：需求是“知识正确且要可追溯、内容更新快（政策/商品/FAQ/内部制度）” → 让模型“查资料再回答”，比微调更可控、更新更轻量。<br>• **考虑微调**：当你遇到以下情况，RAG/Prompt 已无法经济地解决：<br>  - **稳定的输出格式/风格**要求极强（例如固定口径的客服话术、合同条款改写风格）；<br>  - **特定任务准确率上限**被 Prompt/RAG 卡住（如意图分类、信息抽取、特定领域写作风格一致性）；<br>  - **长 Prompt 导致 token 成本太高/延迟太大**，希望把“规则”内化进模型减少上下文；<br>  - 有**足够高质量标注数据**与持续维护能力（否则会越调越差）。<br><br>**3）Trade-off（面试要说清）**<br>• **微调优点**：一致性更强、某些任务上限更高、可减少提示词长度。<br>• **微调风险/成本**：数据清洗标注难、回归评测体系要完善；可能引入“灾难性遗忘”、对新版本基座迁移成本高；还要考虑线上灰度与回滚。<br>• **RAG优点**：知识可更新、可溯源、风险更可控。<br>• **RAG缺点**：检索质量决定上限；链路更长（embedding/向量库/召回/重排），会引入延迟与工程复杂度。 | 是否具备**技术选型的产品化判断**：成本（训练/推理/标注）、效果上限、迭代速度、风险与可维护性；能否把“微调不是万能”讲清楚。 |
| **推理策略（CoT/思维链）** | 什么是 CoT（Chain-of-Thought）？它为什么能提升效果？在真实产品里你会怎么用、怎么控风险？ | **通俗解释**：CoT 就是让模型“把思考步骤写出来再给结论”，对多步推理/复杂约束更友好。<br><br>**1）CoT 的价值（什么时候有效）**<br>• 适合：多步推理（数学/逻辑）、复杂规则决策、需要分解任务的规划类问题（Agent 的 planning）、结构化推导（对比/取舍/归因）。<br>• 原因（PM表述版）：把问题拆成步骤能降低“一步到位猜答案”的概率，提高可解释性与自检空间。<br><br>**2）产品落地怎么用（别只会背概念）**<br>• **显式 CoT（给步骤）**：用于内部工具/专家用户（例如投研分析、代码审查、风控审核），步骤可帮助复核。<br>• **隐式 CoT（不展示步骤）**：面向 C 端时，通常只要结果与关键依据，不一定展示全部推理过程（减少冗长、降低“编造推理”的观感与风险）。可用“先思考后回答/仅输出结论+要点依据”的提示策略。<br>• **与工作流结合**：先让模型输出“计划/子任务列表”，再逐步执行（检索、调用工具、计算），最后汇总，这比单轮长 CoT 更稳定。<br><br>**3）Trade-off：CoT 的成本与风险**<br>• **成本**：输出更长 → token 成本与延迟上升；并发高时费用明显。<br>• **风险**：模型可能“编造看似合理的推理步骤”（伪推理），导致你误以为更可靠。<br><br>**4）控制手段（面试加分点）**<br>• **用结果型校验替代“看推理”**：对关键任务做可自动验证的检查（规则校验、单元测试、数值复算）。<br>• **自一致性/多样采样**：多次生成对比一致性，降低偶发错误（注意成本上升，适合高价值请求）。<br>• **分层输出**：对用户只展示“结论+引用依据+置信提示”，把中间推理留在日志里供运营/质检排查。 | 是否理解 CoT 的**适用边界**与**工程化代价**（token、延迟）；是否知道“可解释≠可靠”，能提出可落地的质量保障方案。 |
| **可靠性与风控（Hallucination 幻觉）** | 大模型“幻觉”是什么？如果你的 AI 产品被投诉生成虚假信息，你会如何止损与长期治理？ | **通俗解释**：幻觉就是模型在“不知道/没证据”时仍给出像真的一样的回答——语言流畅但事实不保证。<br><br>**1）先说明成因（PM可讲的层级）**<br>• 模型本质是“基于上下文的概率生成”，不是数据库检索；在信息缺失、问题超边界或提示不清时会“补全”。<br>• 训练数据噪声、领域知识缺口、RAG 检索失败、工具调用失败未被识别，都可能触发幻觉。<br><br>**2）短期止损（线上应急）**<br>• **收敛入口与场景**：先下线高风险能力/关键词拦截（医疗、法律、金融建议等），或降级到检索结果直出/人工客服。<br>• **增加“无法回答”策略**：缺证据就拒答/引导转人工，明确告知信息来源与时效。<br>• **监控与复盘**：把投诉样本进入事故复盘：触发路径（Prompt/RAG/工具/数据）、影响面、回滚方案。<br><br>**3）长期治理（产品+算法+数据联动）**<br>• **RAG + 引用机制**：对事实性问题默认“先检索再回答”，强制输出引用（文档标题/链接/段落），无召回则拒答。<br>• **质量门禁**：上线前建立评测集（高频问答、极端/对抗样本、业务红线），持续回归；线上用用户反馈+抽检形成闭环。<br>• **置信度与兜底**：根据检索分数/一致性/规则校验给出“可能不确定”的提示，触发人工审核或二次确认。<br>• **内容安全与合规**：敏感领域加规则与审核流（黑白名单、敏感实体识别、输出过滤），并在产品文案里做能力边界声明（但不能只靠免责声明）。<br><br>**4）面试官想听到的关键取舍**<br>• **准确性 vs 覆盖率**：收窄场景会降低覆盖率，但能显著降低风险；先“可控可用”再扩展。<br>• **体验 vs 成本**：更多检索、重排、二次确认会更慢更贵，但对高风险业务值得。 | 是否具备**风险意识**与**可执行的治理体系**：RAG/引用/拒答、评测集与回归、线上监控、人工兜底；能讲清“准确率-覆盖率-成本-体验”的权衡。 |
