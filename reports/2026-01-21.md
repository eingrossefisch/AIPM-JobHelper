| **LLM 原理&边界** | 请用通俗语言解释：LLM 是怎么“工作”的？它的核心能力边界在哪里，哪些承诺不能乱给？ | **一句话通俗解释**：LLM 像一个“读了海量文本的超级输入法/写作助理”，根据上下文去预测下一段最可能出现的词，从而生成回答。<br><br>**它怎么跑通的（PM能讲清的版本）**：<br>1) **预训练**：先在大量公开文本上学“语言规律/知识的统计关联”，学会通顺表达与常识模式。<br>2) **对齐（指令化）**：再通过指令数据、人类偏好反馈（如RLHF/DPO）让它更像“助理”，会按指令回答、少说废话、尽量安全。<br>3) **推理时生成**：每次输出其实是在“逐 token 续写”，并非真正检索数据库或进行严格逻辑证明。<br><br>**核心能力（适合承诺的）**：<br>- 强：**自然语言理解与生成**（总结、改写、写作、分类、结构化抽取）<br>- 强：**弱知识问答/模式推理**（在训练分布内、提示清晰时效果好）<br>- 可工程化增强：配合 **RAG/工具调用** 处理企业知识、实时数据与行动执行。<br><br>**核心边界（不能乱承诺）**：<br>- **幻觉**：会“编得像真的”，尤其在缺少证据/要求过于笼统时；因此“回答所有问题”是高风险承诺。<br>- **实时性/真值性**：默认不保证最新事实；除非接入检索/数据源并做引用校验。<br>- **复杂推理稳定性**：长链路、多约束任务易漂移；需要拆解任务、加校验与回退。<br>- **上下文窗口与成本**：长文/多轮对话会变贵、变慢，也可能遗忘早期信息。<br><br>**产品侧应对（把边界变成可交付）**：<br>- 用 **“回答=基于证据”** 的交互：引用来源、置信度、可追溯链接；无证据则提示“不确定”。<br>- **场景收窄**：先覆盖TOP问题/高频流程，而不是追求全能。<br>- **兜底机制**：转人工、工单、知识库补全闭环；把“模型能力”变成“系统能力”。 | 能否把“生成式概率模型”讲成人话；是否理解幻觉、实时性、推理边界与 token 成本；是否能把技术边界转成产品约束与交付方案。 |
| **RAG / 知识库问答** | 业务说“做个 AI 客服，能回答所有问题”。你会如何拆解？什么时候用 RAG，什么时候要微调/Agent/转人工？ | **一句话通俗解释**：AI客服不是“一个模型就行”，而是“模型 + 企业知识检索 + 规则与人工兜底”的服务系统。<br><br>**需求拆解（PM推进路径）**：<br>1) **澄清目标**：降本（减少人工量）还是增收/体验（提升解决率）？明确覆盖范围：售前/售后/物流/退款等。<br>2) **问题分层**：把“所有问题”拆成：<br>- A类：FAQ/政策类（有标准答案）<br>- B类：订单/账户类（需要查系统数据）<br>- C类：投诉/异常类（高风险、需人工）<br>3) **方案选型（为什么是RAG）**：<br>- **RAG适合**：答案来自企业文档且更新频繁（政策、SOP、活动规则）；不想每次更新都训练模型。<br>- **微调适合**：想固化“语气/格式/分类器能力”、或固定任务（意图识别、字段抽取）且数据稳定。<br>- **Agent/工具调用适合**：需要“查订单/改地址/发优惠券”等动作，必须接业务系统并加权限与审计。<br>- **必须转人工**：法律/医疗/强投诉、资金风险、模型不确定或证据不足场景。<br><br>**RAG落地关键点（PM要抓住的坑）**：<br>- **知识治理**：文档来源、版本、有效期、是否允许对外；切分粒度与标签体系。<br>- **检索质量**：召回不足会导致“答非所问”，召回太宽会导致“胡乱拼接”；需要离线评测集。<br>- **回答策略**：强制“只基于检索到的内容回答”，并**输出引用**；检索为空时拒答/转人工。<br>- **指标闭环**：算法指标（命中率、引用覆盖率、拒答率）、业务指标（自助解决率、转人工率、平均处理时长、满意度）。<br><br>**成本&性能 trade-off**：<br>- RAG有**一次性索引/治理成本**，但推理时避免塞入大量无关上下文，通常更省 token。<br>- 过度依赖长上下文“整本手册塞进去”会让**成本、延迟、错误率**同时上升。 | 是否具备“需求分层+技术选型”能力；是否懂RAG的价值（可更新、可追溯）与落地难点（知识治理/评测/拒答与兜底）；是否有指标体系与闭环意识。 |
| **Agent / 工具调用（Tool Call）& 可靠性** | LLM 的 tool call 和“让 LLM 写一段 Python 去调用函数”有什么区别？在产品里怎么选，如何避免 Agent 乱操作/死循环？ | **一句话通俗解释**：tool call 是“让模型按约定结构去调用你提供的能力”，而写代码是“让模型自由发挥”，前者更可控、可审计、可规模化。<br><br>**两者本质区别（PM视角）**：<br>1) **可控性**：<br>- Tool call：输入/输出有固定 schema（参数、类型），你可以做参数校验、权限控制、风控拦截。<br>- 写代码：自由度大，容易引入不安全逻辑、环境依赖与不可重复结果。<br>2) **稳定性&维护**：<br>- Tool call：工具接口稳定，模型只负责“选择工具+填参数”，更容易回归测试。<br>- 写代码：每次生成可能不同，debug 成本高，难做一致性保障。<br>3) **安全与合规**：<br>- Tool call：天然适合做**审计日志**（谁在何时调用了什么工具、参数是什么）。<br>- 写代码：更难治理（可能访问不该访问的资源、写出危险操作）。<br>4) **能力边界**：<br>- Tool call适合“动作型任务”（查/改/提交/生成单据）。<br>- 写代码更适合“研发辅助/沙盒实验”，不适合直接面向生产用户的关键链路。<br><br>**产品如何选型（推荐策略）**：<br>- 生产系统优先 **tool call + 白名单工具**；写代码仅用于受控沙盒或内部效率工具。<br>- 对高风险动作（退款、改价、发券）采用 **Human-in-the-loop**：先生成方案→展示影响→人工确认→执行。<br><br>**避免 Agent 失控/死循环的设计**：<br>- **终止条件**：最大轮数、最大耗时、预算上限（token/费用）；超限自动降级。<br>- **状态机/工作流**：把任务拆成可验证步骤（plan→act→verify），每步都有检查点。<br>- **权限分级**：只读工具 vs 可写工具；可写工具必须二次确认/审批。<br>- **结果校验**：执行后做一致性检查（例如订单状态是否真的变更），失败则回滚/转人工。 | 是否理解 Agent 的工程化关键：结构化调用、权限、审计与回退；能否用“可靠性与合规”解释选型；是否具备防死循环、防越权的产品安全设计能力。 |
